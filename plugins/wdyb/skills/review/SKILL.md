# review — what do you build?

GitHub の Pull Request の差分を **hunk 単位** で 1 つずつ提示し、ユーザーが「この差分は何をやっているのか」を自分の言葉で書く。全 hunk を書き終えたあとで、はじめて答え合わせ（分析と指摘）を行う。

これは **理解度を測るための学習ツール** である。答えを先に教えてしまうと目的が失われる。

## 絶対に守るルール

1. **収集フェーズ中は正誤を一切言わない。** ユーザーの解釈に対して「そうですね」「正しいです」「惜しいです」などの評価・相槌・ヒントを返さない。受け取ったら次の hunk に進むだけ。
2. **ヒントを与えない。** 差分そのもの以外の情報（関連コード、コミットメッセージの解説、PR 説明文の要約）を収集フェーズで提示しない。ユーザーから明示的に求められた場合のみ、その旨を記録した上で提示する。
3. **ユーザーの解釈は改変しない。** 要約・整形・言い換えをせず、書かれたまま記録する。
4. **分析はコードの実物に基づいて行う。** 推測で指摘しない。必要ならリポジトリのコードを読んで裏を取る。

## 手順

### 1. 対象 PR を決める

引数から PR を特定する。受け付ける形式:

- `123` — PR 番号
- `https://github.com/owner/repo/pull/123` — PR の URL
- 引数なし — `gh pr view --json number` で現在のブランチに紐づく PR を探す。見つからなければユーザーに尋ねる

`gh` が未認証・未インストールの場合はその旨を伝えて中断する。

### 2. 差分を取得する

```bash
gh pr view <番号> --json number,title,url,author,baseRefName,headRefName,body
gh pr diff <番号>
```

URL 指定なら `--repo owner/repo` を付ける。

### 3. hunk に分割する

unified diff を `diff --git` ごとのファイル、`@@ ... @@` ごとの hunk に分割し、通し番号を振る。

以下は解釈の対象から外し、その旨を一覧に明記する（数だけ数えて、質問はしない）:

- lock ファイル（`*.lock`, `package-lock.json`, `go.sum` など）
- 自動生成ファイル、バイナリファイル
- 純粋なリネーム・パーミッション変更のみの差分

分割後、まず全体像を提示する:

```
PR #123 「タイトル」
owner/repo · author · base ← head

変更ファイル: 8 件 / 解釈対象の hunk: 14 件
（除外: package-lock.json ほか 2 ファイル）

1. src/api/client.ts  @@ -12,7 +12,15 @@
2. src/api/client.ts  @@ -40,3 +48,9 @@
...
```

hunk が 25 件を超える場合は、そのまま進めるか / ファイル単位にまとめるか / 対象ファイルを絞るかをユーザーに確認する。

### 4. 解釈を収集する（1 hunk ずつ）

hunk を 1 つ提示し、ユーザーの解釈を待つ。**必ず 1 つずつ。まとめて出さない。**

提示フォーマット:

````
[3/14] src/api/client.ts

```diff
@@ -40,3 +48,9 @@ export class ApiClient {
   （差分本文）
```

これは何をやっていると思いますか？
````

差分が長い場合でも省略せずに全文を出す。

ユーザーの入力に応じた扱い:

| 入力 | 挙動 |
| --- | --- |
| 通常の文章 | 解釈として記録し、次の hunk へ |
| `skip` / 「わからない」「パス」 | 解釈を「（未回答）」として記録し、次の hunk へ |
| `back` / 「戻る」 | 1 つ前の hunk に戻ってやり直す |
| `stop` / 「中断」 | 収集を打ち切り、そこまでの分でフェーズ 5 に進む |

記録は会話の中で保持し、**この段階ではファイルに書き出さない**。

### 5. 分析する（全 hunk を終えてから）

収集が終わったら、はじめて分析に入る。hunk ごとに:

1. その差分が実際に何をしているかを、リポジトリのコードを読んで確認する。呼び出し元・呼び出し先・型定義・テストなど、判断に必要な範囲を実際に読む
2. ユーザーの解釈と突き合わせ、次のいずれかで判定する
   - **正しい** — 意図と効果を捉えている
   - **おしい** — 大筋は合っているが、抜けや不正確な点がある
   - **誤り** — 挙動の理解が実際と食い違っている
   - **未回答** — skip されたもの
3. 判定の根拠を、ファイル名と行番号を挙げて具体的に書く。「〜な気がする」で終わらせない
4. 誤り・おしいの場合は、正しい解釈を書く

最後に全体の傾向をまとめる。「どういう種類の差分で読み違えやすいか」という観点で書くと学習に繋がる（例: 「エラーハンドリングの追加は捉えられているが、非同期処理の実行順序の変化を見落とす傾向がある」）。

### 6. 保存する

カレントディレクトリに `wdyb-<PR番号>.md` を書き出す。既存ファイルがある場合は上書き前にユーザーへ確認する。

フォーマット:

````markdown
# wdyb #123 — <PRタイトル>

- URL: <PRのURL>
- リポジトリ: owner/repo
- 作成者: author
- ブランチ: base ← head
- 実施日: YYYY-MM-DD
- 結果: 正しい 8 / おしい 3 / 誤り 2 / 未回答 1（全 14 hunk）

## 総評

<全体の傾向。読み違えやすいパターンを具体的に>

---

## 1. src/api/client.ts `@@ -12,7 +12,15 @@` — ✅ 正しい

```diff
（差分）
```

**あなたの解釈**

> （ユーザーが書いた文章をそのまま）

**実際の内容**

（実際に何をしているか）

**指摘**

（判定の根拠。正しい場合は「補足」として、関連する背景を書いてもよい）

---

## 2. src/api/client.ts `@@ -40,3 +48,9 @@` — ⚠️ おしい

...
````

判定の見出し記号は `✅ 正しい` / `⚠️ おしい` / `❌ 誤り` / `➖ 未回答` を使う。

書き出したらパスを伝えて終了する。
