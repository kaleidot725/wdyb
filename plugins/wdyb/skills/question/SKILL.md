# question — what do you build?

PR の差分を hunk 単位で 1 つずつ提示し、ユーザーが「これは何をやっているか」を自分の言葉で書く。全部書き終えてから答え合わせをする。

**理解度を測るツールである。答えを先に教えたら意味がない。**

## 絶対に守るルール

- 収集フェーズ中は正誤を一切言わない。評価も相槌もヒントも返さず、受け取ったら次へ進むだけ
- hunk は 1 つずつ出す。まとめて出さない
- ユーザーの解釈は要約・整形せず、書かれたまま記録する
- 分析は実コードを読んで裏を取る。推測で指摘しない

## 手順

### 1. hunk に分割する

引数から PR を特定する（PR 番号 / PR の URL / 引数なしなら現在のブランチの PR）。

```bash
gh pr view <番号> --json number,title,url,author,baseRefName,headRefName
gh pr diff <番号>
```

差分を `@@` ごとの hunk に分割して通し番号を振る。lock ファイル・自動生成物・バイナリ・リネームのみの差分は対象外にする。

全体像（PR タイトル、対象 hunk 数、除外したファイル、hunk 一覧）を提示してから始める。25 件を超える場合は、そのまま進めるか対象を絞るかを確認する。

### 2. hunk ごとに回答を記入してもらう

1 つ提示して解釈を待つ。差分は省略せず全文を出す。

````
[3/14] src/api/client.ts

```diff
@@ -40,3 +48,9 @@ export class ApiClient {
（差分本文）
```

これは何をやっていると思いますか？
````

`skip`（未回答として次へ）、`back`（前に戻る）、`stop`（打ち切って手順 3 へ）を受け付ける。記録は会話中に保持し、まだファイルに書かない。

### 3. 全部終わったら理解が合っているか確認する

hunk ごとに、リポジトリの実コード（呼び出し元・呼び出し先・型定義・テストなど）を読んで実際の挙動を確認し、ユーザーの解釈と突き合わせて判定する。

`✅ 正しい` / `⚠️ おしい` / `❌ 誤り` / `➖ 未回答`

判定の根拠はファイル名と行番号を挙げて具体的に書く。誤り・おしいの場合は正しい解釈を示す。

### 4. レポートを保存する

`wdyb-<PR番号>.md` に書き出す（既存なら上書き前に確認）。総評には「どういう種類の差分で読み違えやすいか」を書く。例:「エラーハンドリングの追加は捉えられているが、非同期処理の実行順序の変化を見落とす傾向がある」

````markdown
# wdyb #123 — <PRタイトル>

- URL / リポジトリ / 作成者 / ブランチ / 実施日
- 結果: 正しい 8 / おしい 3 / 誤り 2 / 未回答 1（全 14 hunk）

## 総評

<読み違えやすいパターンを具体的に>
````
